Your client's purchase register never leaves your laptop.

Concord matches GSTR-2B against the month's purchase register and tells you three things: what input tax credit is at risk, what you have not claimed, and exactly who to call. No login, no upload, no subscription — a folder of Python you run on your own machine.

Three questions, every month

Reconciling 2B by hand is not hard, it is endless. Two hundred invoices, three different invoice-numbering habits, and one supplier who filed in the last week. The work that matters is not the matching — it is what the matching finds.

Risk

What can be disallowed

Credit claimed in the books that GSTR-2B does not support. The 3B says one thing, the portal says another.

Missed

What you have not claimed

Invoices sitting in 2B that never reached the books. Credit bought and paid for, then forgotten.

Action

Who to call

One paste-ready WhatsApp message per supplier, naming the invoice and the amount, largest first.

Install

Python 3.9 or newer is the only requirement. There are no packages to install — no openpyxl, no pandas, nothing that can break on a client's machine.

  1. Get the code

    Clone it, or download the ZIP from GitHub and unzip it anywhere.

    git clone https://github.com/chirag120670598-dotcom/concord.git
cd concord

  2. Download GSTR-2B JSON from the portal

    Services → Returns → Returns Dashboard → pick FY and period → GSTR-2B → Generate JSON File to Download. Keep it in Downloads; no API keys, no portal login inside the tool.

  3. Run it against the register

    python3 -m concord reconcile \
    --2b    ~/Downloads/gstr2b_092026.json \
    --books ~/client/purchase-register.xlsx

    Add --csv recon.csv for a row-by-row sheet to send the client, or --json to feed another script.

  4. Send the supplier messages

    python3 -m concord chase --2b … --books … --out messages/

    One .txt per supplier, worded so their accountant can act without phoning you back.

Why it does not simply guess

Matching by invoice number alone is how bad reconciliation tools produce confident nonsense. A supplier's 145th invoice is not a unique identifier — every supplier has one. Concord runs five passes, cheapest first, and puts three rules above all of them.

Rule 1

A number alone is not a match

GST/2026/0145, INV-145 and 145 are the same document only if the amount agrees too.

Rule 2

A different GSTIN is a different supplier

No fuzzy GSTINs, no "probably the same party". Wrong pairings create credit that does not exist.

Rule 3

Credit notes stay on their own side

A credit note can never be matched against an invoice. Both the portal convention and the register convention are understood.

Your judgement is not thrown away either. When you confirm a pair the tool had to think about, --save-memory remembers it, so the same supplier costs nothing next month. Exact matches are never stored — they need no memory.

What it will not do

Read this before you trust a number

  • It does not match 100%, and never will. On clean files expect roughly 85–92%, and lower on messy ones. Anything above that on a first pass is usually a tool pairing documents it should have left apart.
  • It saves time; it does not recover money. The at-risk figure tells you where to look. Getting the supplier to file their GSTR-1 is what actually recovers the credit.
  • The bundled sample is synthetic. It exercises every code path but says nothing about your Tally export — real files are still needed to call this validated.
  • Only the first sheet of an .xlsx is read. Merged cells, formulas and pivot tables are not parsed. Flatten the register to one sheet first. Old .xls files are not supported — save as .xlsx or .csv.
  • GSTR-2B against the books is the entire scope. No GSTR-1, no GSTR-9, no e-invoicing, no TDS, no filing. Nothing here talks to the GST portal; you still file the return yourself.
  • It is not tax advice. A human decides every treatment. The tool's only job is to put the right document in front of that human.
  • Tested on Ubuntu, Windows and macOS on Python 3.9, 3.12 and 3.13, on every push. Windows found a real bug on the first run: cmd.exe cannot encode ₹, so the report died partway when piped to a file. Fixed, and pinned by a test.
  • This has not been through a filing season. The engine is young. Your judgement calls from the first few months will be worth more than anything claimed on this page.

Questions a CA actually asks

Does this upload my client's data anywhere?

No. There is no network code in the package at all — no HTTP client, no socket, no analytics. You can disconnect the laptop from the internet and the run is byte-identical. For a professional, this is an ethics requirement before it is a feature: client ledgers are confidential, and a cloud tool makes that confidentiality a contract term instead of a fact.

What if my register has different column names?

The reader scores column headers instead of requiring exact names, so Invoice No, Bill No, Inv. No. and Voucher No all resolve. Title rows above the header — the "Purchase Register 2026-27" line that Tally loves — are skipped. If a required column truly is missing, the error lists the headers it did see, so you know what to rename.

What happens to the documents it cannot match?

They go into one of four buckets and none are dropped: only in 2B (unclaimed), only in the books (at risk), value mismatch (both sides present, money differs), credit blocked by the portal. Nothing is silently discarded, and a document that pairs on number but disagrees on money is reported rather than matched.

Do I need to know Python?

Can I modify it for my firm?

Yes. Apache-2.0 — use it commercially, change it, ship it inside your own practice. If you improve the matching, the correction is welcome upstream, because a reconciliation that fails on your file is probably failing on someone else's too.
